# 도담(DODAM) Pull Request 컨벤션

> 적용 대상: `dodam-frontend`, `dodam-backend`, `dodam-ai` 전체 저장소

## 1. PR 생성 원칙

1. **개발 시작 전 GitHub Issue를 생성**합니다. PR은 해당 Issue와 연결합니다.
2. **일반 작업 PR의 대상 브랜치는 반드시 `develop`**입니다.
3. 하나의 PR에는 하나의 명확한 목적만 담고, 리뷰 가능한 크기로 유지합니다.
4. 작성자는 PR 제출 전 셀프 리뷰를 하고 관련 빌드·테스트를 수행합니다.
5. **최소 1명의 리뷰어 승인(Approve)** 및 필수 검증 통과 후 병합합니다. 작성자 본인의 검토는 승인 인원에 포함하지 않습니다.
6. 권장 병합 방식은 **Squash and merge**입니다.
7. `main` 반영은 배포·릴리스 PR 등 별도 흐름으로 관리합니다. `hotfix` 예외는 팀에 사전 공유하고 `develop`에도 동기화합니다.

## 2. PR 제목 형식

```text
<type>(<scope>): <한국어 변경 내용>
```

- **PR 제목의 변경 설명은 한국어**로 작성합니다.
- `type`과 선택적 `scope`는 영어로 작성합니다.
- `type`은 커밋 컨벤션의 유형을 따릅니다.
- 파일 나열보다 사용자·시스템 관점의 변경 사항을 적습니다.
- 제목 끝에 마침표를 붙이지 않습니다.

좋은 예시:

```text
feat(health-record): 육아 메모 시간 선택 기능 추가
fix(auth): 토큰 갱신 오류 수정
refactor(user): 사용자 조회 및 변경 서비스 분리
docs: 팀 개발 컨벤션 정리
test(chat): 메시지 유효성 검증 테스트 추가
```

피해야 할 예시:

```text
feat: add memo time selection
로그인 수정
기능 구현 완료
fix: 여러 오류 수정
```

> **주의:** PR 제목은 한국어지만 Squash 병합으로 만들어지는 **최종 커밋 제목은 영어**여야 합니다. 병합 화면에서 커밋 제목을 수정합니다.

## 3. PR 본문 템플릿

PR 본문은 **한국어**로 작성합니다. API 이름, 코드 식별자, 명령어 등은 원문 표기를 유지합니다.

```md
## 무엇을 구현했나요?
- 구현한 기능이나 수정한 문제를 설명해 주세요.
- 사용자 또는 시스템 관점의 주요 변경 사항을 작성해 주세요.

## 참고할 사항
- 리뷰어가 중점적으로 확인할 부분을 작성해 주세요.
- API·DB 변경, 다른 저장소 연동 영향, 환경 변수, 화면 이미지 등을 적어 주세요.
- 별도 참고 사항이 없다면 `없음`으로 작성해 주세요.

## 테스트
- 실행한 테스트: `명령어`
- 수동 확인: 확인한 시나리오와 결과
- 테스트하지 못한 항목: 사유를 작성해 주세요.

## 연결된 이슈
- Closes #이슈번호
```

예시:

```md
## 무엇을 구현했나요?
- 육아 메모 작성 시 기록 날짜뿐 아니라 시간을 선택할 수 있도록 구현했습니다.
- 선택한 시간을 API 요청에 포함하고 타임라인에도 시간순으로 표시합니다.

## 참고할 사항
- 기존 기록에 시간이 없으면 날짜만 표시됩니다.
- `recordedAt` 필드가 추가되어 Spring 백엔드 변경 PR이 먼저 반영되어야 합니다.

## 테스트
- 실행한 테스트: `npm run build`
- 메모 생성·수정 후 선택한 시간이 유지되는 것을 확인했습니다.
- 시간이 없는 기존 메모도 정상 표시되는 것을 확인했습니다.

## 연결된 이슈
- Closes #12
```

같은 Issue를 여러 저장소에서 사용하는 경우에는 **Issue가 있는 저장소의 전체 주소**(`Closes 조직명/저장소명#12`)로 연결합니다. 자동 종료 여부는 GitHub의 기본 브랜치와 PR 병합 조건에 영향을 받으므로, `develop`에 병합한 뒤 Issue 상태를 확인하고 필요하면 수동으로 닫습니다.

## 4. 검증 기준

| 변경 영역 | PR 전 최소 검증 |
| --- | --- |
| Frontend (React/Vite) | `npm run build` + 변경 화면 모바일/데스크톱 수동 확인 |
| Spring Backend | `./mvnw test` (Windows: `.\mvnw.cmd test`) |
| AI Backend | `ruff check .` + `pytest` |
| API 계약 변경 | 연동 저장소와 요청·응답·오류 코드 확인 |
| DB 마이그레이션 | 빈 DB와 기존 데이터가 있는 DB에서 적용 확인 |

- 정상 흐름뿐 아니라 오류·빈 상태·권한 없음·외부 서비스 실패를 고려합니다.
- 자동 테스트가 어려운 경우 PR에 수동 검증 결과와 미검증 사유를 남깁니다.
- 민감정보, 의료 문서, 토큰, 인증정보가 로그·스크린샷·커밋에 포함되지 않았는지 확인합니다.

## 5. 리뷰 및 병합

- 리뷰어는 코드 취향보다 **정확성, 보안, API 호환성, 테스트 가능성**을 우선합니다.
- 반드시 수정해야 하는 의견은 `Request changes`, 선택적인 제안은 `Suggestion` 또는 `Nit`으로 구분합니다.
- 리뷰 반영 뒤 무엇을 반영했는지 댓글을 남깁니다.
- **최소 1명 Approve**, 필수 체크 통과, 충돌 해결 뒤 병합합니다.
- 권장 방식인 **Squash and merge**에서 최종 커밋 제목이 영어 컨벤션을 지키는지 확인합니다.
- PR 병합 후 해당 브랜치를 삭제하고 Issue 상태를 확인합니다.
- GitHub의 브랜치 보호 규칙/Rulesets에서 `develop`의 PR 필수 및 **승인 1명 이상**을 설정하는 것을 권장합니다.

## 6. Definition of Done

- [ ] 요구사항 및 Issue 완료 조건을 충족했다
- [ ] 작업 브랜치가 브랜치 컨벤션을 따른다
- [ ] 커밋 제목은 영어 컨벤션을 따른다
- [ ] PR 제목·본문은 한국어 규칙을 따른다
- [ ] PR 대상이 `develop`이다 (긴급·릴리스 예외 제외)
- [ ] 관련 테스트·빌드가 통과했다
- [ ] 오류, 빈 상태, 권한, 민감정보 노출을 확인했다
- [ ] API/DB 변경 시 연동 호환성과 변경 영향을 확인했다
- [ ] 관련 문서 및 `.env.example`을 갱신했다
- [ ] 최소 1명의 리뷰어 승인을 받았다
- [ ] 충돌 및 필수 검증을 해결했고 최종 Squash 커밋 제목이 영어다
